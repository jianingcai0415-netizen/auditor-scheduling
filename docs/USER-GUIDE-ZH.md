# 审核员调配系统 · 中文操作手册

> 适用版本：数据库 v24（订单审批 + 方案定稿）· 更新于 2026-10-21  
> 读者：第一次使用系统的业务人员；以及需要熟悉全流程的项目负责人。  
> 配套：`AUDITOR-SCHEDULING-ZH.md`（数据模型与接口）、`ORDER-APPROVAL-REDESIGN.md`（流程设计取舍）。

## 一、先理解四层数据

系统里所有操作都围绕这四层，认清它们就不会迷路：

```
订单 Audit Order        客户委托的一次认证项目（例：某公司 ISO 9001 监督审核）
  └─ 阶段 Phase         订单拆成的时间块（文件审查 / 现场审核 / 整改验证）
       └─ 班次 Shift    阶段按「所需人数」展开的工作名额，例如 3 人 → 3 条班次
            └─ 分配 Assignment   班次上填谁（employee_id）。填了就等于生效
```

另外三个支撑对象：

| 对象      | 作用                                        |
| ------- | ----------------------------------------- |
| **审核员** | 资源。带资格（技能 + 等级 + 有效期）、常驻城市、缓冲时间、启停用       |
| **地点**  | 城市/站点，带经纬度。两地之间的通行时间由高德自动算，参与派单打分         |
| **技能**  | 认证标准（QMS-9001、EMS-14001…）。班次要什么、人有什么，两边匹配 |

**核心概念：方案（Plan）**  
方案是一份「这批班次打算派谁」的快照，它本身不生效；**定稿**时才把快照写进班次，此刻生效。  
方案只有两个状态：`草案` 和 `已定稿`，外加 `已被新版本替代`。

## 二、启动与登录

1. 双击 `scripts/start-windows.bat`（分发包里是根目录的 `启动审核员调配系统.bat`）；
2. 浏览器自动打开 `http://localhost:8081`；
3. 用账号登录（当前演示环境：`selftest` / `SelfTest2026!`，管理员）。

> 首次全新安装时系统会引导创建第一个管理员；之后新建账号默认需要管理员批准。  
> 右上角可切换「部门」与「界面语言（中文/英文）」，部门决定你看到哪一套数据。

## 四、完整流程（每一步都写清「怎么做 → 产生什么 → 去哪看」）

### 第 1 步：准备基础数据（只需一次）

**怎么做**（配置页，管理员）

| 分区                   | 做什么                              |
| -------------------- | -------------------------------- |
| 部门                   | 建机构（演示环境只有「中国审核中心」）              |
| 技能                   | 建认证标准，如 `QMS-9001`、`HACCP`       |
| 地点                   | 建城市并填经纬度（有坐标才会出现在地图上，也才参与通行时间计算） |
| 通用配置                 | 首页封面与欢迎文案                        |
| 邮件设置 / 邮件模板 / PDF 模板 | 需要发邮件时才配                         |
| 求解器设置                | 求解时长、上下文天数等                      |

**产生什么**：`structures` / `skills` / `locations` 等基础表各增若干行。  
**去哪看**：地点页、技能页（配置→技能）、地图页（新增城市会立刻出现点位）。

> ⚠️ 地点一旦新增/修改/删除，系统会**清空转场时间矩阵**，下次派单时重新向高德计算  
> （30 个城市约 870 对，需要几十秒）。所以地点尽量一次配好。

---

### 第 2 步：维护审核员

**怎么做**：审核员页 → 新增；填工号、姓名、邮箱、常驻城市、缓冲时间；在资格区挂技能（等级 + 证书 + 有效期）。

**产生什么**：`employees` +1；每条资格写 `employee_skills` +1。  
**去哪看**：审核员列表；地图上该城市人数 +1。

> 资格有效期不覆盖任务时段的，派单时会被硬约束排除（不是警告，是直接不出现）。

---

### 第 3 步：录入订单

**怎么做**（工作台「订单与阶段」）

1. 填写订单号、客户、项目、负责人、优先级 → 点 **创建订单**；
2. 展开该订单 → 点 **添加阶段**；填阶段名、开始/结束时间、地点、**所需人数**、是否需要组长、资格要求。

**产生什么**

| 动作   | 数据库变化                                                               |
| ---- | ------------------------------------------------------------------- |
| 创建订单 | `audit_orders` +1，状态 `草案`                                           |
| 添加阶段 | `audit_order_phases` +1，**并按「所需人数」自动生成同样数量的班次**（3 人 → 3 条 `shifts`） |

第二条是最容易被忽略的效果：**阶段一建，班次就有了**。所以「所需人数」改大改小，  
班次数量会跟着增减（已被占用的班次会拒绝删除并报错）。

**去哪看**：订单展开后的阶段表格；「排班管理」的时间轴上也能看到这批新班次。

---

### 第 4 步：审批订单

**怎么做**：订单行 → **提交审批**；审批人收到后点 **批准** 或 **退回**（退回必须写原因）。

**产生什么**

| 动作   | 数据库变化                                             | 审计事件                    |
| ---- | ------------------------------------------------- | ----------------------- |
| 提交审批 | `status=SUBMITTED`，写 `submitted_at`               | `AUDIT_ORDER_SUBMITTED` |
| 批准   | `status=APPROVED`，写 `approved_at` / `approved_by` | `AUDIT_ORDER_APPROVED`  |
| 退回   | `status=REJECTED`，写 `reject_reason`               | `AUDIT_ORDER_REJECTED`  |

**规则**：只有 `已批准` 的订单才能排班。「查候选」按钮在未批准时是灰的；强行调用接口会返回  
`AUDIT_ORDER_NOT_APPROVED`。已提交/已批准的订单，编辑时**只能改内容、不能改状态**（防止绕过审批）。

**去哪看**：订单头部的状态徽章；展开后能看到「提交于 / 某某批准于 / 退回原因」。

---

### 第 5 步：排班（两条路线，选一条）

#### 路线 A · 逐个名额挑人（适合单子少、要精挑）

1. 订单行 → **查候选**（必须是已批准且有就绪阶段）；
2. 系统按 5 个维度打分并排序，顶部能看到权重与版本：
   | 维度  | 默认  | 含义             |
   | --- | --- | -------------- |
   | 能力  | 40% | 资格是否匹配、等级够不够   |
   | 位置  | 30% | 通行时间（高德算的转场矩阵） |
   | 空闲度 | 15% | 全局已排小时数        |
   | 连续性 | 10% | 是否连续跟同一客户      |
   | 年龄  | 5%  | 未采集时按中性 50 分   |
3. 可点「AI 初筛」让大模型在**规则筛出的候选内**给建议（不能越权选人）；
4. 看完推荐后，点 **生成该订单排程草案** —— 注意：草案从**全部未分配**开始，推荐结果不会自动占人；
5. 打开草案 → 逐个名额点 **选择并锁定** → 在弹窗里挑人、选「选择原因」→ 点 **选择**；
6. 名额全部填满、无风险后 → **定稿**。

> 顺序容易记错：**先建草案，再往里面填人**。候选列表只是"看"，不产生任何占用。

**产生什么**

| 动作    | 数据库变化                                                                                 |
| ----- | ------------------------------------------------------------------------------------- |
| 查候选   | **只读**，不写任何表（分数是现算的）                                                                  |
| 生成草案  | `schedule_plans` +1（来源=按订单），`schedule_plan_assignments` 每个班次 +1 行快照，`employee_id` 全为空 |
| 选择并锁定 | 该行 `plan_assignments.employee_id` 写入 + `locked=1`，审计 `SCHEDULE_ASSIGNMENT_CHANGED`    |

**去哪看**：工作台「排程方案」tab 多出一条 `草案`；点「查看」能看到每个名额对应的人。

#### 路线 B · 求解器批量排（适合一次排一批）

1. 排班管理页 → 选时间窗；
2. 点 **求解**（Timefold 优化，几秒到几十秒）；
3. 检查时间轴上的结果，需要时手工调整；
4. 点 **保存结果**。

**产生什么**

| 动作   | 数据库变化                                                      |
| ---- | ---------------------------------------------------------- |
| 求解   | 只在前端内存里算，**不写库**                                           |
| 保存结果 | 写 `shifts.employee_id`（此刻生效）；若有覆盖这些班次的草案且已全部排满，**自动定稿**该方案 |

**去哪看**：时间轴上的名字；工作台「排程方案」里对应方案变成 `已定稿`。

> 路线 A 与 B 的差别：A 由你决定每个人，B 由算法决定。两者最终都落到同一张 `shifts` 表。

---

### 第 6 步：定稿

**怎么做**（路线 A 才需要）：方案详情 → 检查「人员完成度」→ 点 **定稿** → 确认弹窗 → 确认定稿。

**产生什么**（这是整个系统最关键的一次写入）

1. 把方案快照里的 `employee_id` 写进 `shifts`，并写 `published_plan_id` 标记来源；
2. 时间窗重叠的旧 `已定稿` 方案 → 标为 `已被新版本替代`；
3. 定稿前自动做一次安全备份；
4. 写审计 `SCHEDULE_PLAN_FINALIZED`。

**前置条件**：名额不能有空缺、不能有未处理的风险（时间冲突、资格失效、人员状态变化等）。  
有缺口时「定稿」按钮是灰的，鼠标悬停会告诉你还差几个人。

**去哪看**

- 方案状态变 `已定稿`，步骤条走到第二步；
- **地图上对应的人从「空闲」变「在岗」**（如果定稿的班次覆盖当前时刻）；
- 排班管理页时间轴上出现名字。

---

### 第 7 步：查看与汇报

| 想看什么           | 去哪                                                 |
| -------------- | -------------------------------------------------- |
| 全国谁在哪、谁在岗      | **审核员地图**：三档口径（此刻 / 今日 / 未来7天），点城市看人，点人看订单         |
| 某段时间每个地点的人手够不够 | **报表 → 覆盖率**：选地点 + 周期 → 每地点一份横版 PDF，空缺班次会标出并计数     |
| 某个审核员这段时间的行程   | **报表 → 发送**：每人生成一份个人 PDF，可直接邮件发送                   |
| 某个方案的分配明细      | 工作台 → 排程方案 → 查看；或 **导出 Excel**                     |
| 谁在什么时候改了什么     | 工作台 → **操作日志**（审批人与管理员可见，最近 300 条）                 |
| 数据当前是什么状态      | 地图页脚「数据时间」；工作台顶部四张卡（已批准订单 / 待排班草案 / 待审批订单 / 已定稿方案） |

| 查候选      | **不写库**                                        | 候选列表与分数         | —                 |
| 生成草案     | `schedule_plans` + `schedule_plan_assignments` | 方案列表多一条「草案」     | **删除草案**（仅草案可删）   |
| 锁定人员     | `schedule_plan_assignments.employee_id`        | 方案详情里该名额有名字     | 可换人               |
| 定稿       | `shifts.employee_id` + `published_plan_id`     | 方案「已定稿」，地图变在岗   | 不可撤销；要改用**新建修订**  |
| 求解       | **不写库**                                        | 时间轴预览           | 重新求解即可            |
| 保存结果     | `shifts.employee_id`（并可能自动定稿方案）                | 时间轴落定           | 再次求解 + 保存可覆盖      |
| 紧急换人     | 新建一个修订方案                                       | 旧方案仍有效，新方案待定稿   | 不想要就删草案           |
| Excel 导入 | 先预览，确认后才写                                      | 导入任务列表 + 结果计数   | 无回滚，需靠备份          |

## 六、日常场景

**「临时有人请假，要换人」**  
方案详情 → 该名额 → **紧急换人** → 系统自动建一个修订草案 → 选替补 → 填原因 → 定稿。  
原方案在新方案定稿前一直有效，不会出现"空窗"。

**「订单要取消」**  
订单行 → 编辑订单 → 状态改为已取消（已批准/已提交的订单也允许关闭）。  
已排的班次需要到方案里另行处理。

**「方案改不动了」**  
已定稿的方案不可编辑，这是刻意设计。用 **新建修订** 复制一份，改完再定稿；  
旧方案会自动变成「已被新版本替代」，但它在重叠时段之外的安排仍然有效——地图上不会凭空消失。

**「数据要备份/恢复」**  
配置 → 备份：可手动建、下载、删除、恢复。此外每次定稿前系统会自动做一次安全备份。

## 七、常见问题

**Q：为什么「查候选」是灰的？**  
订单没批准，或没有「就绪」状态的阶段。先提交审批并批准。

**Q：为什么候选列表里看不到某个人？**  
硬约束先过滤：资格不匹配/证书过期、时间冲突、不可用日期、缓冲不足、已停用。  
每个名额下方能展开「排除原因」，按原因分组，能直接看到被谁排除了。

**Q：定稿后地图上没变化？**  
地图「此刻」口径只统计**当前时刻**有班次覆盖的人。定稿的班次如果在下周，切到「未来7天」才看得到。

**Q：两个人都说派了自己？**  
不可能同时生效：定稿时后定稿的方案会把时间窗重叠的旧方案标为「已被新版本替代」，  
班次上只保留最后一次写入的人。

**Q：求解结果和方案是什么关系？**  
求解是"算"，方案是"记"。求解完不保存，什么都不会发生；保存后如果存在覆盖这些班次的草案，  
系统会把分配回填进快照并定稿——保证事后追溯看到的是"最后派了谁"，而不是"当初打算派谁"。

**Q：能改界面文字吗？**  
可以。配置 → 本地化，改完刷新页面生效（文案存在数据库里，不写死在前端）。
